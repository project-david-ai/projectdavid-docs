# Configuration Reference

Project David Platform stores deployment configuration and generated credentials in the runtime directory's `.env` file. Application API keys, registered inference provider keys and MCP credentials are managed separately through the API.

## Runtime directory

All commands must address the same deployment. Platform resolves the runtime directory using:

1. `--runtime-dir` (a global CLI option, before any subcommand).
2. `PDAVID_RUNTIME_HOME`.
3. The current working directory.

The first startup generates configuration and credentials. Subsequent startup operations reconcile generated defaults and load the existing `.env`.

Keep the runtime directory and persistent data backed up. If `.env` is missing but `.projectdavid-instance-id` exists, Platform refuses to generate replacement secrets. Recover the original configuration rather than creating a fresh instance over existing data.

## Update configuration

Run from the existing runtime directory. For example, change the application log level:

```bash
pdavid configure --set LOG_LEVEL=DEBUG
pdavid --mode up --force-recreate
```

Container recreation can interrupt active runs; schedule configuration changes accordingly. Restore `LOG_LEVEL=INFO` after troubleshooting.

`--set KEY=VALUE` can be repeated to update multiple settings. The command writes `.env` directly; it does not validate the meaning of arbitrary keys or rotate credentials in their backing services. Do not put plaintext credentials on command lines or in shell history. The interactive option only prompts for the CLI's predefined user-required settings, not every configuration variable.

## Network and inference

| Variable | Packaged default | Purpose |
|---|---|---|
| `DOWNLOAD_BASE_URL` | `http://localhost:80/v1/files/download` | Base address for generated download links |
| `BASE_URL_HEALTH` | `http://localhost:80/v1/health` | Deployment health endpoint |
| `SANDBOX_SERVER_URL` | `http://sandbox:8000` | Internal sandbox endpoint |
| `SHELL_SERVER_URL` | `ws://sandbox:8000/ws/computer` | Internal computer session endpoint |
| `SHELL_SERVER_EXTERNAL_URL` | `ws://localhost:8000/ws/computer` | External computer session address |
| `CODE_EXECUTION_URL` | `ws://sandbox:8000/ws/execute` | Internal code execution endpoint |
| `HYPERBOLIC_BASE_URL` | `https://api.hyperbolic.ai/inference/v1` | Hyperbolic inference endpoint |
| `TOGETHER_BASE_URL` | `https://api.together.xyz/v1` | Together inference endpoint |

`ASSISTANTS_BASE_URL` is also generated by Platform. The supplied implementation contains a malformed default (`http: // nginx_proxy: 80`). Verify the actual service address for your deployment before relying on this setting; do not use that literal value as a URL.

For remote deployments, ensure externally consumed URLs resolve from the client network. Internal service addresses should remain appropriate to the Compose network. Configuring a public URL does not itself configure TLS, DNS or proxy routing.

Platform migrates the known obsolete Hyperbolic default (`https://api.hyperbolic.xyz/v1`) in generated runtime files; custom endpoint values are preserved by that migration.

## Runtime settings

| Variable | Packaged default | Purpose |
|---|---|---|
| `LOG_LEVEL` | `INFO` | Application log verbosity |
| `PYTHONUNBUFFERED` | `1` | Unbuffered Python output |
| `AUTO_MIGRATE` | `1` | Database migration setting |
| `SHARED_PATH` | `./shared_data` | Shared storage directory |
| `WEB_FAVICONS_ENABLED` | `true` | Web favicon setting |
| `DISABLE_FIREJAIL` | `true` | Firejail disable setting |

The defaults above describe the Platform generator, not a guarantee of the running service's effective configuration. In particular, do not infer sandbox isolation from the default `DISABLE_FIREJAIL` value. Verify the sandbox configuration and isolation controls before exposing the deployment to untrusted workloads.

## Persistent services

These settings normally remain unchanged in an existing deployment.

| Variable | Packaged default | Purpose |
|---|---|---|
| `MYSQL_HOST` | `db` | Internal database host |
| `MYSQL_PORT` | `3306` | Internal database port |
| `MYSQL_DATABASE` | `entities_db` | Database name |
| `MYSQL_USER` | `api_user` | Database application user |
| `REDIS_URL` | `redis://redis:6379/0` | Redis connection string |
| `SMBCLIENT_SERVER` | `samba_server` | File share server |
| `SMBCLIENT_SHARE` | `cosmic_share` | File share name |
| `SMBCLIENT_USERNAME` | `samba_user` | File share user |
| `SMBCLIENT_PORT` | `445` | File share port |
| `SAMBA_USERID` | `1000` | File ownership UID setting |
| `SAMBA_GROUPID` | `1000` | File ownership GID setting |

`DATABASE_URL` is constructed from database settings and the generated password during initialization. `SPECIAL_DB_URL` is generated when a host port mapping can be resolved. Treat both connection strings as secrets. Changing individual database variables does not automatically synchronize existing database credentials or rebuild the connection strings through `configure`.

## Generated credentials and identifiers

Platform generates the following credentials during initialization. Preserve them with the associated runtime data.

| Variables | Category |
|---|---|
| `MYSQL_PASSWORD`, `MYSQL_ROOT_PASSWORD` | Database credentials |
| `SMBCLIENT_PASSWORD` | File share credential |
| `API_KEY`, `SANDBOX_AUTH_SECRET` | Internal credentials |
| `SECRET_KEY`, `DEFAULT_SECRET_KEY`, `SIGNED_URL_SECRET`, `SEARXNG_SECRET_KEY` | Service secrets |
| `PROJECT_DAVID_CREDENTIAL_KEY`, `PROJECT_DAVID_PROVIDER_KEY_HMAC_KEY` | Credential-management key material |

The `TOOL_CODE_INTERPRETER`, `TOOL_WEB_SEARCH`, `TOOL_COMPUTER` and `TOOL_VECTOR_STORE_SEARCH` identifiers are also generated at initialization. They are resource identifiers, not API credentials. Preserve them across restarts and recovery.

`ADMIN_USER_EMAIL` defaults to `admin@example.com`; `ADMIN_USER_ID` and `ADMIN_KEY_PREFIX` default to empty strings. These generated settings are separate from the canonical administrator credential provisioned by Core.

## Application and administrator access

`pdavid bootstrap-admin` obtains the canonical admin credential from Core and persists its plaintext in the runtime `.env` as `ADMIN_API_KEY`. The ordinary CLI output reports the user and key prefix, not the full secret. For supported handoff and recovery options, see [Self-hosted Setup](/docs/boot_strap_guide).

Do not replace `ADMIN_API_KEY` with an arbitrary string in `.env`: that does not register a valid key in Core. Use a dedicated application key for normal API requests. Register tenant-owned inference provider credentials through the provider key API and manage MCP credentials through the MCP API. See [Authentication](/docs/api_keys).

## Credential rotation and recovery

Configuration changes and credential rotation are separate operations. The CLI warns about some sensitive changes only **after** writing the new values; those warnings are not an enforcement mechanism or a complete rotation policy.

- Database and file share credentials require coordinated changes to the backing services, configuration and dependent connection strings.
- Signing and credential-management keys may affect access to existing signed links or stored credentials. Preserve the originals until a supported migration and recovery procedure is verified.
- Rotate administrator, application, provider and MCP credentials through their respective credential-management interfaces where supported.

Back up configuration and persistent data before maintenance. Use `pdavid --mode down_only` and `pdavid --mode up` for a planned full restart when required by a verified procedure.

Never use volume deletion as a credential rotation or recovery step. `--clear-volumes` removes Docker Compose volumes and can destroy persistent data. No general-purpose in-place rotation procedure for generated service secrets is established by this CLI.
